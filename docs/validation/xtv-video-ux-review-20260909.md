# XTV 实机录屏 UX / UI 评审与 RFC-001 优先级

日期：2026-09-09。结论：最值得先解决的是详情加载状态的可信度，以及遥控器操作时的方向感。现有单帖阅读、媒体查看和父页面恢复值得保留；通信迁移必须服务于这些可验收的用户行为。

## 证据与方法

- 视频：[用户剪辑版](../../.scratch/recordings/session_20260909_145734/edited/manual_test_trimmed_with_remote-00.01.14.366-00.12.42.733.mp4)，实际时长 **11:33.33**，1280×720 / 30 fps。
- 按每 8 秒抽帧覆盖全片，再对加载错误、详情切换、图片查看、视频控制、操作菜单及 HOME 恢复片段逐秒复核，并检查原分辨率截图。这是视觉与操作流程评审，未做音频评测或逐帧性能测量。
- 本文时间均为这个文件的播放位置。右下角黄色按键文字属于录制 HUD，时间仅为估算，且沿用前一版剪辑时间轴。
- 视频已删去长段等待，又经二次剪辑，不能从片中间隔推算真实加载耗时、按键延迟或丢键率。画面倾斜和外围黑边不直接归因于应用布局；也不根据压缩截图宣称字体对比度检测不合格。
- 对照 [RFC-001](../rfcs/rfc-001-direct-session-native-messaging.md) 与 [实机可行性研究](rfc-001-feasibility.md)。录屏没有构建标识，因此不能证明它与当前 HEAD 的 UI 完全一致。
- 关键截图及抽帧表位于 [评审素材目录](../../.scratch/ux-video-review-20260909/)。本评审没有修改应用或 RFC。

## 总体设计判断

模板化反模式检查：没有明显的营销模板式装饰堆砌。当前视觉特征是深色阅读界面、单帖主体、蓝色焦点和独立媒体查看器。精致度主要受制于焦点层级不统一、详情阅读比例固定、局部控件尺寸偏小，以及加载状态反复切换。

值得保留的三点：

1. **时间线一屏集中展示一条帖子。** 07:20 的图文布局能让作者、正文与媒体成为明确主体，适合投影阅读，不宜为了“丰富”改成密集信息墙。
2. **媒体能力已经存在。** 03:10 起可进入查看器并放大图片；07:17 起的视频控制条提供暂停、全屏、跳转和静音，白色实心选中态相当清楚。
3. **阅读上下文在部分路径得到保留。** 视频中多次详情返回时间线；09:17 左右从系统界面恢复到原详情。此前实体 BACK 研究也确认过一次主文档及焦点保留，应将其固化为回归要求。

## 五项优先改进

### 1. P0：详情页错误提示失真，加载过程缺少稳定的状态表达

**证据：** 00:24 左侧骨架屏；00:30–00:33 出现“帖子暂不可用／该帖子可能已被作者删除或链接失效”，按钮是“返回上一页”；00:34 又显示骨架，00:39 显示原帖正文，评论稍后出现。[00:32 截图](../../.scratch/ux-video-review-20260909/frame-032.jpg)。这段足以确认用户看到的状态发生矛盾，但不能仅凭剪辑和 HUD 判断是否触发重试、服务器返回了什么，或是哪段代码误判。

**影响：** 用户可能相信帖子已经失效而放弃阅读。全屏加载、骨架、错误、再次骨架构成多次视觉中断。仅让动画更平滑不能解决错误语义。

**改法：**

- 区分“正在准备详情”“正文可读、评论仍在加载”“暂未加载成功”“服务端明确判定不可用”。不能只因暂时没有匹配到正文就推断删除或链接失效。
- 保留稳定的详情外壳和已知作者／帖子摘要，并明确其为预览；新数据就绪后在原位置更新。预览不能冒充新页面成功加载。
- 正文满足展示条件后先允许阅读。评论失败只在评论区显示恢复入口，不拖住整个详情页。
- 暂时失败提供“重试”和“返回”，错误原因未知时使用中性文案。已知删除、权限限制等则根据实际证据显示对应状态。

**验收：** 延迟正文、延迟评论、断网、明确不可用分别可控复现；慢正文不会闪现“已删除”；评论未就绪时正文可滚动；重试不重复打开详情；任一等待状态都可返回。

相关技能：`harden`、`clarify`。这是最高优先级的行为修复。

### 2. P1：焦点需要同时解释“当前区域”和“确认将执行什么”

**证据：** 01:04 评论区外框与“写评论”输入行同时描边；02:32 评论容器、选中评论、底部输入行形成多层边界。[01:04](../../.scratch/ux-video-review-20260909/frame-064.jpg)、[02:32](../../.scratch/ux-video-review-20260909/frame-152.jpg)。底部已有随状态变化的按键说明，这是优点，但它承担了过多解释工作。

**影响：** 初次使用者需要低头读小字，才能判断上下键是在滚正文、选评论还是移动输入目标。进入回复详情后，标题仍是泛化的“帖子详情”，不容易确认自己位于原帖还是回复层。

**改法：**

- 当前区域使用轻微底色或标题标记；真正可执行的焦点使用统一、明显的描边与填充，避免容器和项目采用同等强度的框。
- 明确正文、评论、媒体、弹层的方向键契约。进入评论区恢复上次选中的评论，回正文恢复原滚动位置。
- 简短提示只显示当前场景最有用的两三项；例如“↑↓ 阅读 · → 评论”。评论有更多内容时，在评论区显示清楚的滚动提示。
- 回复详情显示“回复 @作者”或可理解的父帖关系；返回后落回刚才选中的评论。

**验收：** 在实际观看距离下，不读取整行帮助文字也能指出焦点及 OK 的作用；评论刷新不抢走焦点；连续 BACK 逐层退出，不在区域间循环。此方向与 Android TV 对清楚、一致焦点及可预测返回的要求一致。[官方导航原则](https://developer.android.com/training/tv/get-started/navigation?hl=en)

相关技能：`clarify`、`normalize`。这是导航规则和视觉反馈共同承担的问题，不能靠加一个边框完成。

### 3. P1：详情布局应照顾长文、短文与评论的不同阅读需求

**证据：** 01:04 左侧只有一句回复，却保留巨大固定阅读容器；02:32 右侧长评论带图片，被压在窄列中；03:44–04:40 的长文与截图需要持续滚动。空白本身不是缺陷，问题是正文已有富余空间时，另一侧仍显局促。

**影响：** 视线在作者、正文、底部计数与窄评论之间移动距离较大。长评论中的文本和嵌图难以成为真正可读的内容。

**改法：**

- 保留时间线单帖布局。详情进入时优先正文；切到评论阅读后，适度扩大评论阅读区，或支持将选中评论展开为完整阅读视图。
- 短文不画满屏空框，作者、正文和互动信息形成紧凑的一组；长文保持适中的行宽、足够的行距和稳定的滚动区域。
- 明确正文、作者、时间／计数、辅助说明的字号层级。评论正文不能仅因它是次栏就过度缩小。
- 布局变化在进入阅读模式时进行，避免每次移动评论焦点都让两栏来回伸缩。

**验收：** 使用一句话、中文长文、英文长段落、多图、带媒体长评论这五类样本，在用户实际座位测试阅读；可快速进入正文或评论，退出展开视图恢复原锚点。字号先在投影上验证，再固定设计参数。TV 排版应优先保证可读性。[官方字体原则](https://developer.android.google.cn/design/ui/tv/guides/styles/typography?hl=en)

相关技能：`distill`、`normalize`。

### 4. P1：媒体入口与控制模式要更容易发现

**证据：** 02:58–03:07 出现时间线→加载／详情骨架→时间线，随后 03:10 进入媒体查看并放大；07:07–07:14 也先进入详情加载后返回，07:17 起打开媒体控制，07:29 左右进入全屏。这些路径说明有两个不同目标可选：阅读帖子、观看媒体；不能据此断定用户误操作或按键失灵。[07:20 控制条](../../.scratch/ux-video-review-20260909/frame-440.jpg)

**影响：** 用户可能需要先试探才能发现怎样直接看媒体。控制条有清楚选中态，但六个等权按钮让播放、定位、音量和关闭混在一条操作序列中；进度主要通过秒数表达。

**改法：**

- 保持卡片 OK 打开帖子的规则；媒体有可见、可聚焦的入口，并在获得焦点时显示“播放／查看媒体”的明确提示。不能依赖用户记住未提示的快捷键。
- 统一卡片、媒体控件、全屏三种模式的按键说明。确认始终执行当前焦点对应动作；全屏切换应保留播放位置，是否继续播放取决于切换前的状态。
- 增加可读的进度条，区分播放、暂停、缓冲；将播放／定位设为主要操作，全屏和静音作次级操作。
- “关闭”改成具体结果，例如“退出控制”；如它实际停止播放，则明确“停止播放”。BACK 关闭当前临时层后恢复媒体焦点。

**验收：** 首次使用者能够直接找到播放入口；视频暂停后切换全屏仍暂停且时间不重置；缓冲时能返回；长按方向键不会触发重复打开或重复关闭。录屏中的停帧不能单独证明播放失败，缓冲与网络因素需另行测量。

相关技能：`clarify`、`polish`。保持已有可信键盘输入与媒体用户激活语义。

### 5. P2：建立统一的 TV 视觉尺度，优先修菜单与辅助信息

**证据：** 08:56 的“帖子操作”弹层在整屏中偏小，标题、计数和底部提示集中在小面积中；10:40 的外链行已提供域名，但主标签仍是被截断的 URL。[08:56](../../.scratch/ux-video-review-20260909/frame-536.jpg)、[10:40](../../.scratch/ux-video-review-20260909/frame-640.jpg)

**影响：** 同一应用里，时间线正文、视频控件、菜单使用了不同的视觉尺度。用户能看到有链接，却未必能区分具体内容。

**改法：**

- 统一安全边距、文字等级、控件高度、圆角、默认／聚焦／按下／禁用状态。深色底保留，蓝色集中表达焦点和选中，减少重复细框与装饰光晕。
- 菜单扩大到适合远距离阅读的尺寸；保留少量上下文即可，不需要把背景大幅模糊到认不出正在操作的帖子。
- 外链优先显示可获得的文章标题，域名作为次级信息；没有标题时使用“打开外链 1”等稳定标签并保留域名、可辨认路径，不能凭域名猜出文章含义。
- 辅助说明位置稳定、字号可读，减少长串命令。过渡动画只用于表达焦点、面板开合和状态更新，不额外延长进入内容的时间。

**验收：** 从实际座位可读出菜单动作及外链目标差异；各页面焦点状态看起来属于同一个系统。先统一少量设计变量，再做局部精修。[官方焦点系统](https://developer.android.google.cn/design/ui/tv/guides/styles/focus-system?hl=en)

相关技能：`normalize`、`polish`。

## 次要观察与不要误报的问题

- 11:20 时间线顶部有一条明显蓝色横条，录屏不能确认它代表加载还是阅读进度。需核对其真实语义：加载条完成后应退出；阅读位置指示则应与内容建立清楚关系。
- 回复变成详情主体、再返回原帖，可能是正常层级导航。本次没有证据把它定为“不同 Session 内容串线”。改进父子关系说明即可先降低困惑。
- 09:17 附近 HOME 恢复原详情是正面样本；09:28 后可见最近任务中关闭 XTV，之后重新加载不能算成 HOME 恢复失败。
- 黑边、投影梯形及黄色 HUD 不列入应用视觉修复；截图中的原帖图文由作者提供，也不要求应用重排图片内部文字。
- 一次实体 BACK 通过不等于所有层级通过；不应为增强“安全感”额外增加退出确认。应验证菜单→媒体／详情→父页面→应用根部→系统的实际层级。

## RFC-001：真正需要解决、需要修改及应推迟的内容

RFC 的价值应由“当前页面可靠出现、按键作用于眼前内容、返回后继续阅读”衡量。此次视频不能证明直连通信会消除详情加载慢，也不能证明原始故障发生在哪一跳。

| 决策 | 内容 | 依据及边界 |
| --- | --- | --- |
| 保留并优先 | ready 接受确认、有限恢复、DOM 与 Native 遮罩独立条件 | 先前实机已出现 DOM 就绪而原生遮罩仍在；本片另显示详情状态问题。两者可能发生在不同层，不能合并成一个根因。 |
| 保留并优先 | 按 Session 隔离、可见性校验、旧绑定／旧 Activity 回调失效 | 研究已记录旧回调晚于新 Activity 创建；需要保护前台 UI 和父页状态。 |
| 实施前必须改 | 文档身份与导航权威、Background 的职责 | 已复现新导航开始后旧文档重连且查询仍为 current。当前 RFC 不能靠 Java sender、最后 Port 或随机 documentId 满足承诺。 |
| 纳入产品验收 | 正文可读与评论加载分离、局部失败恢复、返回锚点保留 | 这些是用户能观察的结果；页面内部状态不必全部成为 Native 消息类型。 |
| 单独安排适配层工作 | 错误判定、阅读布局、焦点、媒体入口和菜单 | RFC §4.1 明确保留 tvx://post 等 NavigationDelegate 入口。换 Port 不会自然修好这些体验。 |
| 保留现有路径并清理真实死分支 | GeckoView 可信按键、媒体激活；核对后清理 KeyRouter move/activate/menu | 实机支持可信键盘路径；非 adapter BACK 仍可达，mock 隐藏按钮误消费应另行修复，不能整体删除 KeyRouter。 |
| 暂缓扩张 | 通用 RPC、逐键 ACK、固定高频心跳、全面动态注入重写 | 缺少对应产品需求或充分设备证据。2 秒心跳是否必要应由半开故障和长期运行实验决定。 |

直连可以继续做最小实验，但“必须直连”不应成为先验结论。建议对比两种候选在相同故障场景下的总复杂度：**明确 Session／文档绑定的中继**，以及**直连数据加 Background 文档仲裁**。后者的仲裁候选尚未端到端通过；不能在文档中把它写成已解决。

要真正提升加载速度，应分别记录：用户确认→详情导航、导航→正文可读、正文可读→Native 解除遮罩、评论可读、媒体首帧。保留未剪辑录像与同次运行的关联日志，并记录 APK 身份。已有研究中 Native 收到 ready→View.GONE 回调仅 14–30 ms，而 DOM 准备需要数秒至十余秒；这支持把测量重点放在揭幕前各阶段，但不是实际投影首帧耗时证明。

## 建议实施顺序

1. **详情可靠性闭环：** 补齐阶段观测；修正不可用状态的判定与恢复；正文／评论独立呈现。同时完成 RFC 文档身份方案的小规模验证。
2. **遥控器阅读闭环：** 统一焦点、回复层级、媒体入口和 BACK；将父帖 ID、选中评论、正文滚动位置作为恢复验收内容。具体锚点可留在适配层，不必全部送到 Native。
3. **视觉统一：** 固定字号、间距、控件状态及菜单尺寸，用长短中英文与媒体样本在投影上校准，再精修动画。

进入第二步前需明确两个产品取舍：默认详情是否以正文阅读为主；时间线卡片的 OK 是否始终表示打开帖子。本报告建议两者均保持一致，并提供明确媒体焦点入口。这样可沿用现有用户习惯，同时减少试探操作。
