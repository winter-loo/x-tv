# 全屏阅读模式 — 在正文上按确认键

**验收构建**：`app-debug.apk`，本地 `assembleDebug` 产出并 `adb install -r` 安装到当贝 DBD5X Pro（`192.168.10.100:5555`，阅读器 WebView `com.android.webview 66`）。
**复现脚本**：`node scripts/check-fullscreen-reading.mjs`（只读：只读一次时间线和一条详情，结束前检查全程无写流量）
**原始证据**：`docs/validation/fullscreen-reading-samples.json`

## 一、做了什么

在**时间线正文**和**帖子详情正文**上，如果这条帖子的正文**装不下当前这一栏**，按确认键进入全屏阅读；装得下的帖子，确认键保持原来的含义，一次按键不变。

- 表头（标题／状态／刷新）隐藏。
- 左右布局改为上下布局，**帖子正文在上**，随行的那一栏（时间线是媒体，详情是评论）落到下面。
- 正文列占屏幕 **3/4 宽度**并水平居中。
- 正文分到更高的一份（约 2:1），因为这是阅读模式。
- 返回键退出全屏，回到原来的页面状态——同一条帖子、同样的几何、同样的焦点。

全屏是**每个场景各自的属性**：在时间线上开着全屏进入详情，详情按普通布局打开；从详情返回，时间线仍然是全屏。这正是「回到原页面状态」。

## 二、确认键：短帖不变，长帖多一级

| 位置 | 正文装得下 | 正文装不下 |
|---|---|---|
| 时间线正文 | 打开帖子详情（**与原来完全一致**） | 进入全屏阅读；再按一次打开帖子详情 |
| 详情正文 | 打开媒体查看器（**与原来完全一致**） | 进入全屏阅读；再按一次打开媒体查看器 |

「装不下」不是按字数猜的，是量出来的：`body.scrollHeight - body.clientHeight > 1`，和正文右下角那个「更多」标记用的是**同一个判断**（`clipped()`），所以标记出现的时候，确认键就是全屏阅读。

还有一个例外：X 只发来摘要、正文还没取全的帖子（`complete === false`），确认键仍然直接去取详情——全屏也变不出还没拿到的文字。

底部提示行始终写明当前这一按是什么（`确认 全屏阅读` / `确认 帖子详情` / `确认 查看媒体`），随内容长短实时切换。

不受影响的：媒体栏上的确认仍然直接打开图片／视频；评论栏上的确认仍然直接打开该评论；正文「更多」标记用鼠标点仍然直接进详情（它要负责去取没下发的正文）。

注意同一条帖子在两处的结论可能不同：详情的正文栏比时间线窄（497 vs 720），所以在时间线里装得下的帖子，进详情后可能就装不下了，那时详情里就会提供全屏阅读。下面 `short-post` 一项正好记录了这种情况。

## 三、真机结果（960×540 CSS 像素，dpr 2）

### 先看这条规则在真实时间线上分得开吗

`scan` 记录脚本走过的前 12 条实帖：

```
装不下（clipped）： 第 4、6、8、9、10 条
装得下：            第 1、2、3、5、7、11、12 条
```

12 条里 5 条长、7 条短——两条路径都不是摆设，日常翻时间线两种都会遇到。脚本随后各挑一条真帖跑完整流程。

### 长帖（第 4 条，Jason Zhu）：左右 → 上下

`timeline` → `timeline-fullscreen`：

```
普通：  stage 883×405 @ (38, 70)   post 430 宽 @ x=48   media 410 宽 @ x=502   表头可见  row
全屏：  stage 720×454 @ (120, 22)  post 701×285 @ y=30  media 701×142 @ y=325  表头隐藏  column
```

- **3/4 宽度**：720 / 960 = **0.750**。
- **居中**：左边距 **120**，右边距 **120**。
- **正文在上**：post 底边 315，media 顶边 325。
- **正文优先**：285 高 vs 142 高。

进入前提示行是 `确认 全屏阅读`，进入后变成 `确认 帖子详情　 返回 退出全屏`。

### 短帖（第 1 条，Tibo）：一次按键直接进详情

`short-post` 记录：

```
before: clipped false，help "… 确认 帖子详情 …"
按一次确认
scene:  detail true，reading false，help "… 确认 全屏阅读 …"
```

按一次就进了详情，没有经过全屏——和这次改动之前的行为逐字相同。

而进详情之后 `clipped` 变成了 true：同一条帖子在更窄的详情正文栏里装不下了，于是详情里提示 `确认 全屏阅读`。规则是按当前这一栏算的，不是按帖子贴标签。

### 详情：评论从右边移到下面

`detail` → `detail-fullscreen`：

```
普通：  post 497 宽 @ x=48   comments 343 宽 @ x=569   row
全屏：  post 701×277 @ y=30  comments 701×150 @ y=317  column
```

宽度同样是 720 / 960 = 0.750。

### 上下边界

全屏时表头没了，正文列从 `y=22` 开始而不是贴着 `y=0`——按 #14 定下的安全边距，焦点框（2px 描边 + 4px 外发光）不能压在屏幕边上，脚本里 `full.post.y >= 6` 钉住了这一点（实测 30）。底边 476，与普通布局的 475 只差一个取整像素，底部的状态行和提示行保持原有空间。

## 四、返回键

```
timeline-restored:  stage 与 post 的几何与进入前逐字节相同，位置 4 / 35，作者 Jason Zhu
detail-restored:    仍在详情里（detail: true），几何与进入前相同
back-to-timeline:   回到时间线 4 / 35，作者不变，且仍是全屏（reading: true）
```

`detail-restored` 是关键一项：在全屏详情里按返回，**先退出全屏，不离开详情**；再按一次才回时间线。

`back-to-timeline` 的 `reading: true` 也是对的：这一轮里时间线是带着全屏状态进入详情的，返回后它仍然全屏。

## 五、全程无写入

`no-writes` 记录 `writes: []`。
