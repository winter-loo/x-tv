# Issue #21 — 在时间线顶部按上键实际刷新并展示新帖子

**验收构建**：`app-debug.apk`（`versionName 0.2.0`，`versionCode 2`），本地 `assembleDebug` 产出并 `adb install -r` 安装到当贝 DBD5X Pro（`192.168.10.100:5555`，系统 WebView `com.android.webview 66.0.3359.158`）。
**复现脚本**：`node scripts/check-timeline-refresh.mjs`（只读：只重读时间线并回放，不写入）
**原始证据**：`docs/validation/issue-21-samples.json`

## 一、改了什么

原来到达顶部按上键只是把焦点移到表头的「刷新」小标签，还要再按一次确认；确认走的是「清空列表 → 重新请求 → 骨架屏」，读到一半的位置也没了。

现在顶部上键**自己就是刷新**：

- 已有待应用更新 → 立即合入，焦点落到新首帖，提示写明加入了多少条。
- 没有待应用更新 → 发起一次刷新，表头显示「正在刷新…」，列表原地不动，新帖到达后才替换。
- 刷新中再按上键不会叠加请求；无新内容说「暂无新帖子」；失败说「刷新未完成，按上键重试」，再按上键即重试。

表头的「刷新」不再是焦点站点，只作状态显示。首页返回键回到首帖的行为保持不变（`back()` 里 `state.index > 0` 那条分支未动），顶部上键正是接在它后面。

后台更新只登记不应用：`homeUpdated` 只把新数据挂到 `pendingHome` 并在表头写出「有 N 条新帖」，除非用户还没有过任何交互（冷启动时缓存升级为实时那一次）。真正应用只发生在显式刷新或顶部上键。

## 二、各验收项与证据

### 返回回到首帖，再按上键：有待应用更新则合入，否则发起刷新

`back-to-top` 记录了工单描述的流程：向下读到 `3 / 33`，返回回到 `1 / 33`。随后上键发起刷新（`refresh` 记录）。「已有待应用更新则立即合入」由 `tests/refresh.spec.mjs` 确定性覆盖，并且 `tests/native-reader.spec.mjs` 里「详情阅读期间到达的新首页」一项也改为按一次上键即合入。

### 加载完成显示新增帖子并把焦点放到新首帖；计数与实际列表一致

真机 `refresh` 记录：

```
whileRefreshing: {position: "1 / 33", refresh: "正在刷新…", notice: "正在刷新…"}
arrived:         {position: "1 / 35", notice: "已加入 35 条新帖子"}
truth:           {before: 33, after: 35, fresh: 35}
reportedCount:   35
reads:           ["home request ms=1233 result=ok"]
```

`truth` 是脚本自己从阅读器实际用过的两份 payload 算出来的：刷新前列表里的帖子 ID 与刷新返回的帖子 ID 求差。报出的条数与真值逐次相等，位置回到 `1 / N`。

需要说明为什么「刷新前 33 条、返回 35 条，新增却是 35」：X 的首页是排序流，两次读取返回的帖子集合本就会变，并不保证是同一批。脚本因此不假设「补回被删掉的两条」，而是每次现算真值再比对——这一点是被真机纠正过来的，最初的脚本按「同一份 35 条」写断言，把正确的计数误判成了缺陷。

去重由 `TvXReadData.parse` 保证（解析时按 ID 去重），列表整体替换为服务端返回的顺序。合入后 `pendingHome` 清空，表头的「有 N 条新帖」提示随之消失。

### 后台更新在用户浏览中不抢走位置

`tests/refresh.spec.mjs` 中：读到第 3 条时收到一份带新帖的后台更新，位置仍是 `3 / 3`、当前帖不变；此时按上键是普通导航（到第 2 条），不发请求。真机侧此项未单独构造（无法按需让 X 在恰当时机推送），由自动化覆盖。

### 无新内容明确反馈，失败可重试，连续上键不堆积

- 无新内容 → 「暂无新帖子」，位置与当前帖不变。
- 失败 → 「刷新未完成，按上键重试」，再按上键确实发出第二次请求。
- 连按：真机 `merged-presses` 记录里三次连按（`burstMs` 2259 ms）只产生 1 次读取（`home request ms=1826`）。需要说明的是，每次 `adb input keyevent` 都是一次独立往返，连按跨度与一次读取的耗时是同量级的；多轮实测中也出现过跨度 2944 ms、读取 1.4 s 的情况，那时第三次按键落在第一次刷新完成之后，产生第二次刷新——那是正常的再次刷新，不是堆积。因此设备上断言的是「不堆积」（三次按键不得产生三次读取），**同一刷新窗口内的精确合并**由 `tests/refresh.spec.mjs` 确定性钉住（三次按键 → 1 次请求）。

### 菜单、图片、播放器或正文滚动拥有焦点时，上键执行其自身动作

顶部刷新只在 `state.region === 'post'` 且位于首帖时触发。菜单、媒体查看器、外链等待层都在按键分发的更前面被拦下。自动化覆盖：菜单打开时上键不刷新、查看器打开时上键是缩放、退出查看器后媒体区仍持有上键。真机 `up-is-navigation-below-the-top` 记录显示非首帖位置的上键是普通导航，`reads` 为空。

## 三、回归测试

`tests/refresh.spec.mjs`（9 项）：待应用更新一键合入且不发请求、无待应用更新时发起一次刷新、新帖到达后计数与列表一致且焦点在新首帖、无新内容的反馈、失败与重试、连按只发一个请求、后台更新不抢位置、覆盖层持有上键、刷新标签不再是焦点站点。

`tests/native-reader.spec.mjs` 中「详情阅读期间到达的新首页」一项按新契约改写（上键一次即合入，不再需要第二次确认），覆盖点保留。

全量：Playwright 149 项通过，JVM 单测 31 项通过。四份真机验收脚本（#20 外链、#21 顶部刷新、#22 前台归属、#13 喜欢反馈）都在本构建上重跑通过。

## 四、顺带修掉的一个回归

跑 #22 的真机脚本做回归时发现「打开原帖」交接坏了：`content_ready` 每次内容脚本注入都会到达，而我在 #22 里用它驱动 POST 交接；content.js 收到 `readerAction` 后如果当前路径不对就会导航，导航又注入新的内容脚本、再次触发 `content_ready`——于是每 ~90 ms 重发一次，`TvXReaderBrowser.announced` 每次都被重置，adapter 永远宣告不了，最后超时。

修法是让一次交接对同一个文档只路由一次（`Handoff.routedFrom` / `routedVia`）：从 x.com/home 问一次（它导航到目标帖），到达目标帖后再问一次（此时路径已对，不再导航，adapter 正常宣告）。`HandoffTest` 增加了对应用例。

## 五、本轮未覆盖

- **真机上的「有待应用更新时上键合入」**：需要 X 恰好在用户阅读期间推送新帖，无法按需构造；由自动化确定性覆盖。
- **真机上的刷新失败**：需要在刷新途中断网，本轮未做；失败与重试路径由自动化覆盖。
