# Issue #16 — 恢复帖子与评论的发布时间和完整统计标识

**验收构建**：`app-debug.apk`（`versionName 0.2.0`，`versionCode 2`），本地 `assembleDebug` 产出并 `adb install -r` 安装到当贝 DBD5X Pro（`192.168.10.100:5555`，1920×1080，系统 WebView `com.android.webview 66.0.3359.158`）。
**复现脚本**：`node scripts/check-time-stats.mjs`（只读；`--shots <目录>` 可另存截图，截图含已登录时间线，不入库）
**原始证据**：`docs/validation/issue-16-samples.json`

## 一、改前的状态

- `data.js` 一直在解析 `created_at`，但阅读器从未渲染过它——时间线、详情主帖、评论都看不到发布时间。
- 评论只渲染作者、正文和一张图，**完全没有统计**。
- 统计数字有两处在伪造零值：`replies: legacy.reply_count || 0`、`likes: legacy.favorite_count || 0` 把缺失字段变成 0；`浏览 ' + esc(post.views || '0')` 更是在字段缺失时直接显示「浏览 0」。

## 二、改了什么

- 新增两个时间格式化函数：`timeLabel` 给时间线与评论（刚刚 / N 分钟前 / N 小时前 / N 天前 / 月日；**跨年时带上年份**），`fullTime` 给详情主帖（`2026 年 9 月 10 日 06:29`，含年份与时分）。两者都以 `Date.parse` 失败为准返回空串，**不生成错误日期**。
- 时间渲染在 handle 之后：时间线与评论是相对时间，详情主帖另起一行显示完整时间。
- 评论恢复统计：与主帖同一套 `stats()`，评论数、喜欢数、浏览量各自带图标。
- `data.js` 新增 `count()`：只接受 X 真正发来的数字，缺失一律为 `null`。渲染层 `stat()` 遇到 `null` 就整条不渲染——**真实的 0 会显示为 0，缺失的字段不出现**。三处会显示计数的地方（统计行、评论栏标题、操作菜单计数）都按这个规则处理。
- 计数全部为空时不再留一个空的统计行。

## 三、各验收项与证据

真机 `timeline-post` 与 `detail` 记录：

```
时间线主帖   time "8 小时前"    stats "评论 51 喜欢 978 浏览 75656"
详情主帖     time "2026 年 9 月 10 日 06:29"
             stats "评论 51 喜欢 978 浏览 75656"
评论         36 条，其中带时间 36 条，缺图标的数字 0 个
             样本 {"5 小时前", "评论 2 喜欢 8 浏览 2445"}
                  {"1 小时前", "评论 0 喜欢 2 浏览 621"}
                  {"5 小时前", "评论 0 喜欢 0 浏览 1612"}
```

### 时间线、详情主帖、首批及分页评论均显示发布时间；新发布评论即时展示时也带时间

真机上 36 条评论全部带时间（`withTime` 等于 `comments`）。分页评论与新发布评论回显在自动化里覆盖：翻页取回的第三条评论显示「5 分钟前」；走完整的写评论通道（菜单 → 写评论 → 结果回填）后，新评论出现在最前面并显示「刚刚」。

### 近期用明确的相对时间，较早显示日期，详情含年份与时分

自动化用假时钟固定「现在」，逐档验证：20 秒前→刚刚，45 分钟前→45 分钟前，10 天前→8 月 31 日，400 天前→2025 年 …。详情主帖的完整时间在真机上是 `2026 年 9 月 10 日 06:29`，脚本断言里必须同时匹配到四位年份和 `时:分`。

### 评论数、喜欢数、浏览量均有明确且一致的图标

脚本对每条评论的每个 `.stat` 检查是否含 `svg`，`numbersWithoutIcon` 为 0。评论与主帖共用同一组图标。

### 真实零值与接口缺失区分处理

真机样本里出现了真实的 `评论 0`、`喜欢 0`——它们照常显示。缺失字段的处理由自动化钉住：只给 `favorite_count` 的帖子只渲染一个统计项，不出现「评论」「浏览」；`created_at` 缺失或不可解析时不渲染时间，并断言页面上不出现 `Invalid` 或 `NaN`。

### 时间和统计为只读，不加入遥控器操作焦点

`.stats` 与 `.time` 里没有 `button`、`a` 或 `tabindex`；在详情按确认不会发出任何写请求。喜欢与评论仍从菜单进入。

### 投影仪确认字号、间距和图标可辨认

脚本读的是实际计算样式（CSS 像素，dpr 2，即设备像素翻倍）：

| 元素 | 字号 | 图标 |
| :--- | :--- | :--- |
| 详情主帖统计 | 13.4 px（设备 26.8 px） | 15.8 px（设备 31.6 px） |
| 详情主帖完整时间 | 12 px（设备 24 px） | — |
| 评论统计 | 11.5 px（设备 23 px） | 13 px（设备 26 px） |

## 四、本轮修掉的一个显示缺陷

详情主帖的作者块原本是固定 `height:9vh`，加上第三行完整时间后内容溢出，真机截图里作者名的上半截被切掉。改为 `min-height` 让它随内容增高，并加了断言：名字不得高于作者块顶部、时间不得超出其底部。

## 五、顺带修掉一个真实回归

跑六份真机脚本做回归时，#20 外链验收开始间歇失败（三次里失败两次）：交接明明开在
`termany.sh`，会话却提交了 `x.com/home`。把所有 `mSession.loadUri` 收进一个带来源标记
的入口后，日志说清楚了：

```
15:00:52.671  load by=x-home   url=https://x.com/home      启动预热发出的
15:00:55.975  handoff open EXTERNAL target=https://termany.sh/
15:00:55.976  load by=handoff  url=https://termany.sh/
15:00:56.737  handoff loading url=https://x.com/home       ← 3.3 秒前那次才提交，把后发的挤掉
```

也就是说，启动预热的 x.com 导航要几秒才提交；用户在这段窗口里打开外链，后发的导航会
输掉。`fb6b327` 在外链关闭时也会立刻预热 x.com，进一步放大了这个窗口。

修法是让交接在**别人的文档抢先提交**时把会话拿回来：`onLocationChange` 里若本次交接
仍未等到自己的文档（`Handoff.arrived()` 为假），就重新 `driveHandoff()`。另外交接开始
前先 `mSession.stop()`，外链关闭后的预热推迟 1.2 秒且只在没有交接在飞时执行。

用一个专门构造竞态的探针（启动 2.6 秒后立刻开外链）验证重驱确实发生：

```
handoff open EXTERNAL target=https://termany.sh/
handoff loading url=about:blank          ← 别人的文档抢先提交
handoff load by=handoff url=https://termany.sh/   ← 重新拿回会话
handoff loading url=https://termany.sh/
handoff shown kind=EXTERNAL at=https://termany.sh/
```

## 七、本轮未覆盖

- **真机上的分页评论与新发布评论**：分页需要评论数超过首批返回量并滚到底部，新发布评论则是写操作，本轮都没有在真机上构造；两者由自动化确定性覆盖。
- **真机上的缺失时间**：需要 X 返回没有 `created_at` 的条目，无法按需构造；由自动化覆盖。
